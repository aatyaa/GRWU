From Data File to Claim

What does the work actually look like, and how do you make a number someone else can check?

By Attia A. Gadallah·5 October 2026· 20 min read· preview

The first four articles each taught one skill: reading a ring, taking a signal apart into tones, saying how sure you are, and fitting a model. Real work strings them together, and the result is a sentence in a paper. Between the data and that sentence there are dozens of steps, and any of them can go wrong without a sound.

This article follows one small claim from a public data file to a sentence, then breaks each link on purpose to see which habits would have caught the break. None of the habits is clever. All of them are what separates a number from a number someone else can check.

It starts at the Gravitational Wave Open Science Center, which publishes the detectors’ recordings for anyone to use. This file holds 4,096 seconds from LIGO Hanford, 4,096 numbers every second: its sampling rate. It contains GW150914, the first black-hole merger ever detected.

A short program in this site’s data pipeline cuts out 32 seconds around the event. It stores each number divided by 1 × 10⁻²¹, and writes that factor down beside the data, along with the sampling rate. Anyone reading the numbers must put the factor back.

The program also writes down a fingerprint of the file: its SHA-256, 64 characters computed from every byte. Change a single byte and the fingerprint changes completely. This site recomputes it every time it loads the file, and refuses a file that does not match.

Then the analysis: the spectrum from Every Signal Is a Chord, averaged over 63 one-second segments by Welch’s method. The code was compared with scipy’s, number by number, before it was used here.

And the claim. Every part of it can be traced: which file, which seconds, which fingerprint, which method, which test. That trail is what makes it a result rather than an assertion.

Break a link

Now break the chain on purpose. Pick a mistake and watch what it does to the claim, and what would have caught it. The wrong numbers below are not made up: each one was computed from the same file, with the mistake in place.

The most dangerous mistakes are the ones that give reasonable-looking numbers. A frequency four times too high still looks like a frequency. That is why each check works without knowing the answer: the rate is read from the file, the size is compared with what a detector can measure, and the fingerprint is compared with the one published.

A check that needs the right answer to work is not a check.

The last option is not a mistake at all, and it teaches the most. Averaging four-second segments instead of one-second ones moves the quietest point from 278 Hz to 112.5 Hz. Both computations are correct. The detector was about equally quiet over a broad stretch, and which point is lowest depends on the method. So a better claim is one that survives the choice: between 100 and 300 Hz, the noise sat near 8.1 × 10⁻²⁴ per √Hz with one-second segments, and 8.0 × 10⁻²⁴ with four-second ones.

Test your code against a reference

Every function this site applies to data was first run beside an independent program, usually scipy or numpy, on the same inputs, and the two answers compared number by number. It sounds like overkill until you meet the Hann window.

The window that tapers each segment before a spectrum is computed comes in two kinds. The symmetric one ends at zero on both sides; it is what np.hanning returns. The periodic one is what scipy’s spectrum uses; it leaves out the final zero, so that copies placed end to end repeat smoothly. Fredric Harris explained in 1978 why spectral estimates need the periodic kind. On a plot they look the same.

A common mistake

“If the plot looks right, the code is right.”

The two Hann windows differ by up to a third at length 8, and both look like a smooth hump. Shifted spectra, a factor of two in a normalisation, a window of the wrong kind: none of these shows on a plot. A test against an independent reference shows all of them.

Which digits are real

The spectrum above has no randomness in it: run it twice and you get the same numbers to the last digit. A sampler is different. It draws random numbers, so its median comes out a little different on every run.

A seed fixes the random numbers, so the same code gives the same samples every time. That is essential for checking. But it hides a question: which digits would change with a different seed? Below, a made-up posterior, 6 Hz wide, is sampled with twenty different seeds.

With a thousand samples, the medians wander by about 0.2 Hz, so the digit after the decimal point is noise. With a hundred thousand they wander by 0.03 Hz, and one more digit holds. But the posterior is 6 Hz wide either way. The honest quote is 250 ± 6 Hz, and the extra digits say something about the computer, not about the black hole.

Quote a number to the precision of its error bar, not the precision of your computer.

The math: how much a sampled median wanders
AssumeN independent samples from a bell-shaped posterior of spread σ.
  1. Var⁡(m^)≈14N p(m)2\operatorname{Var}(\hat m) \approx \frac{1}{4 N\, p(m)^2}Var(m^)≈4Np(m)21​

    The median of N samples scatters around the true median by an amount set by how dense the posterior is there, p(m).

  2. p(m)=12π σ  ⇒  σm^≈π2 σN≈1.25 σNp(m) = \frac{1}{\sqrt{2\pi}\,\sigma} \;\Rightarrow\; \sigma_{\hat m} \approx \sqrt{\frac{\pi}{2}}\,\frac{\sigma}{\sqrt N} \approx 1.25\,\frac{\sigma}{\sqrt N}p(m)=2π​σ1​⇒σm^​≈2π​​N​σ​≈1.25N​σ​

    For a bell curve, the median wanders by about 1.25 σ/√N: a quarter of a hertz for σ = 6 Hz and N = 1000.

  3. N→NeffN \to N_{\text{eff}}N→Neff​

    For samples from a chain that remembers itself, use the effective number of samples from How Sure Is Sure?, which can be far smaller.

What it means.

The wander shrinks only as one over √N: a hundred times more samples buys one more digit. The width σ of the posterior does not shrink at all.

Reading someone else’s posterior

For each detection, the collaborations publish their posterior samples alongside the data: thousands of rows, one per sample, with a column for each parameter. The real files are in a format called HDF5, and tools such as PESummary read them. Inside, the job is the same as below: pick a column by its name, take its median, and quote a credible interval.

Read a posterior file

What a claim should carry

In 2013 Geir Kjetil Sandve and colleagues wrote ten simple rules for computational work that others can repeat. Most of them have appeared in this article already. Record how every result was produced. Never edit data by hand. Note the random seeds. Keep the data behind every plot. Connect every number in the text to the code that made it.

A claim that follows them carries a short trail with it:

  • the data, with where it came from and its fingerprint;
  • the method, with the choices made, such as the segment length;
  • the code, with its version and the tests it passed against a reference;
  • the seeds, if anything was random;
  • the uncertainty, quoted to the precision it deserves;
  • the assumptions, including the model, which What the Wrong Model Knows showed can fail while every check passes.

This article follows its own advice. Every number it quotes about GW150914 is computed from the file when the site is built, and the build stops if the file’s fingerprint changes.
